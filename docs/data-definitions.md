# Rounds generated analytics assets

This is a portfolio demonstration on synthetic data. It is not a medical device, has not been validated for clinical use, and must not be used to make decisions about real patients.

These artifacts are computed from 2,000 Massachusetts patients generated by official Synthea build `d9d07a6`, seed `20260923`, reference and simulation end `2026-09-22`. They are the sample run, not a 20,000-patient run. Source provenance and checksums are in the parent directory's `provenance.json`.

## Regenerate and test

From the project root:

```powershell
& '.\.venv\Scripts\python.exe' '.\.cache\rounds-data\build_analytics.py'
& '.\.venv\Scripts\python.exe' '.\.cache\rounds-data\test_analytics.py'
```

Python dependencies are pandas and DuckDB, with a pandas-compatible parquet reader for the tests. The local `.deid-salt` preserves pseudonyms and offsets across runs. Keep this file private; do not deploy it. A new salt intentionally creates different pseudonyms and shifted calendar dates.

## Artifact boundaries

- Public: `manifest.json`, `aggregate-tables.json`, `feature-metadata.json`, `build-summary.json`, `ed_daily.csv` and this documentation.
- Private: `private-patients.json`, all warehouse parquet files, `features.parquet` and `hosp12m.parquet`. These contain synthetic row-level information and must remain outside the static site bundle. Patient views require the application's token and persistent audit boundary.
- `warehouse-schema.json` documents nine reduced OMOP-shaped tables. This is not a complete OMOP CDM v5.4 implementation. Source codes are retained without licensed standard-concept mapping; source-code presence must not be described as standard vocabulary mapping accuracy.
- `manifest.schema` describes only the four public aggregate tables actually available to browser SQL.

## De-identification

Before analytic queries, the pipeline selects allowed columns, replaces source patient and encounter UUIDs with separate HMAC-SHA256 namespaces, and shifts every patient date by one constant offset in the range -180 to +180 days. Observation ends receive the same offset, so age, duration, lookback and follow-up intervals remain consistent. The exported person table excludes birth dates and all direct identifying fields; ages are capped at 90 and the oldest age band is `90+`. Source textual observation values, addresses, coordinates, postal codes, income and household-size values are excluded. Clinical source descriptions are standardized Synthea labels, not unstructured patient notes.

The limited private payload contains at most 60 people, 10 timeline entries and 10 laboratory observations per person. Its gate rejects extra patient fields, source UUIDs, SSNs and email patterns, and refuses an empty payload. This is a tested synthetic-data protection demonstration, not a HIPAA Safe Harbor or anonymity certification. The published k-anonymity diagnostic can show groups below five; it does not certify the private rows. Aggregate cohort cells below five are suppressed as null, without a claim of formal disclosure-control completeness.

## Definitions and limits

- An admission is a source encounter explicitly classified `inpatient`; a visit is not reclassified from a procedure label.
- Readmission is the next all-cause inpatient start strictly after index discharge and within 30 days. A discharge is eligible only when its full 30-day window ends before or at that person's shifted observation end and death does not occur during that window. Incomplete windows have a null target, never a zero. Planned returns and transfers are not adjudicated, so this is not a CMS unplanned readmission measure.
- Admission model features are available strictly before admission. Prior visit counts use the preceding 365 days. Condition dates have day precision, so condition counts exclude the entire admission day. Active medication counts require a start before admission and an absent end or end at/after admission. No subsequent discharge information is a feature.
- `target_los_days` is elapsed inpatient start-to-stop time. It is an outcome only.
- `hosp12m.parquet` uses annual January 1 adult indices from 2016 through 2026. This is an annual population risk model, not a primary-care-visit-triggered model. `target_hosp12m` requires complete 365-day follow-up and excludes death within the window. `target_next365_cost` sums source encounter total claim amounts over the same future interval. These amounts are synthetic billed claims, not paid costs or clinical need.
- Per-patient shifts can change cross-person calendar ordering. Any model using them must be labeled a shifted-calendar temporal evaluation; a 360-day boundary buffer can conservatively prevent order reversal across adjacent splits. ED daily aggregate dates use the original system calendar because they contain no person-level data.
- The ten cohorts are lifetime matches to observed SNOMED source-code descriptions. They are reusable and queryable but not clinically validated phenotypes. Active disease, incidence and severity are not implied.
- The ten measures are simplified documentation or data-coverage proportions with explicit denominators. They are not certified quality measures. A missing recent observation is not automatically a clinical care gap.
- ICU census, NEWS2, bed occupancy, eGFR, PDC, surgical complications, standard-concept mapping accuracy and external clinical transportability are not established by these assets. Unavailable values remain null with reasons.
- Thirteen observed-data checks assess referential integrity, ordering, completeness, classes and censoring. No defect injector was run, so detection sensitivity is not claimed.

## Verification

Fifteen independent tests cover the private payload and deliberate identifier violations, empty-input refusal, direct-field rejection, 200 raw-to-shifted interval comparisons, observation-end shifts, censoring and its exact boundary, 200 independently recomputed feature rows, measure arithmetic, cohort SQL counts, public identifier exclusion, low-count cell suppression, warehouse allowlists and the statement/no-em-dash gate. Full test output is stored at `../analytics-test.log`.
